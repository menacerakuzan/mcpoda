# @proyav/prozorro

MCP-сервер до відкритих даних **Prozorro**: державні та комунальні закупівлі України.
Без ключів API і без реєстрації, бо джерела публічні. Сервер лише читає.

Частина проєкту [ПРОЯВ](../../README.md) — Департамент цифрового розвитку, інформаційної
політики та кіберзахисту Одеської обласної державної адміністрації.

## Підключення

Сервер працює у двох режимах, і для людини різниця велика.

**Через URL.** Нічого не встановлювати, нічого не качати: індекс живе на сервері,
людина вставляє п'ять рядків і працює.

```json
{
  "mcpServers": {
    "proyav": {
      "url": "https://mcp.proyav.od.ua/mcp"
    }
  }
}
```

**Локально.** Для роботи офлайн або коли запити не мають виходити з машини.

```json
{
  "mcpServers": {
    "proyav-prozorro": {
      "command": "npx",
      "args": ["-y", "@proyav/prozorro"]
    }
  }
}
```

Обидва режими піднімають ті самі інструменти з того самого коду: різниця лише
в транспорті (stdio проти Streamable HTTP) і в тому, чий диск тримає індекс.

## Tools

| Tool | Що робить |
|---|---|
| `proyav_search_tenders` | Повнотекстовий пошук процедур: текст, статус, регіон, діапазон сум, пагінація |
| `proyav_get_tender` | Картка процедури за внутрішнім id або номером `UA-…`: позиції, учасники, переможець |
| `proyav_recent_tenders` | Стрічка змін: що відбувається просто зараз або від вказаної дати |
| `proyav_search_index` | Пошук по локальному індексу: ЄДРПОУ, CPV, період, українська морфологія |
| `proyav_index_status` | Скільки процедур в індексі, за який період і яка частка має назву й суму |
| `proyav_price_benchmark` | Ціна процедури проти медіани схожих: відповідь на «ми не переплачуємо?» |
| `proyav_aggregate_spend` | Обсяги за замовниками, регіонами, кодами CPV, місяцями |
| `proyav_compare_buyers` | Скільки різні замовники платили за той самий предмет |

Аналітичні інструменти працюють лише по локальному індексу і разом із числами повертають
покриття: скільки процедур у вибірці вже мають суму. Неповний індекс дає занижені суми,
і відповідь про це каже прямо, бо агрегат це те місце, де неповнота бреше переконливо.

Кожен tool повертає компактну вижимку. Сирий запис Prozorro доступний окремо
(`proyav_get_tender` з `full: true`) і важить десятки кілобайт, тому не є типовою відповіддю.

## Розгортання по HTTP

```bash
npm run build
node dist/serve.js        # PORT, HOST, RATE_LIMIT з оточення
```

`/mcp` — сам протокол, `/health` — стан і розмір індексу для моніторингу.

Сесії свідомо вимкнені: кожен запит самодостатній, тому процес можна перезапускати
чи тримати в кількох копіях, і жодна розмова цього не помітить. Обмеження частоти
за замовчуванням 240 запитів на хвилину з адреси, бо точка публічна.

Що потрібно серверу: Node 22 або новіший, близько 5 ГБ диска під індекс,
`./scripts/build-index.sh` один раз і `node dist/cli.js update` у cron щоночі.
Назовні виставляти через проксі з TLS.

## Джерела даних

Перевірено 2026-08-25 живими запитами.

**1. Пошуковий сервіс `prozorro.gov.ua/api/search/tenders`** — тільки POST,
`text` обов'язковий і непорожній, `page` нумерується з 1 і повертається у відповіді луною
(без `page` відповідь каже `page: 0` і віддає ту саму першу сторінку),
`status` приймає масив. Стеля: 10 000 збігів на запит.
`per_page` приймається і мовчки ігнорується: сторінка завжди рівно 20 записів, і відповідь
повертає `per_page: 20`, що б ви не надіслали. Тому `limit` понад 20 сервер набирає сам,
дочитуючи наступні сторінки.
Фільтрів за регіоном, CPV чи ЄДРПОУ немає: `cpv` і `edrpou` мовчки ігноруються,
`region` очікує числовий код і поводиться неконсистентно, тому ми його не використовуємо
і фільтруємо регіон уже на своєму боці.

**2. Центральна база `public.api.openprocurement.org/api/2.5`** — повний запис процедури
за внутрішнім id та хронологічна стрічка змін. Стрічка приймає `limit` до 1000, `descending=1`
і `offset` у вигляді дати `РРРР-ММ-ДД`.
`opt_fields` працює лише для вузького переліку: `status`, `tenderID`, `procuringEntity`,
`procurementMethodType`. Поля `title`, `value`, `items`, `awards` у стрічку не потрапляють
і потребують окремого запиту картки.

## Локальний індекс

Індекс живе файлом на цій машині (`~/.proyav/prozorro.sqlite`, шлях перевизначає `PROYAV_DB`)
і будується двома проходами. Нічого нікуди не надсилається.

Найпростіше — лишити збірку на ніч одним скриптом:

```bash
./scripts/build-index.sh            # усе: свіже, історія з 2015, збагачення
./scripts/build-index.sh --years=5  # лише останні роки
./scripts/build-index.sh --recent   # тільки свіже, близько півгодини
```

Зупиняти можна будь-коли: Ctrl+C або просто закрити ноутбук. Наступний запуск
продовжить з курсора, а не почне спочатку.

Окремі команди, якщо потрібен контроль:

```bash
npx proyav-prozorro crawl --recent      # свіжі процедури першими
npx proyav-prozorro crawl               # історія з 2015 року
npx proyav-prozorro enrich --limit=500  # назви, суми та CPV, найновіші першими
npx proyav-prozorro update              # щоденний догін: зміни від курсора плюс збагачення
npx proyav-prozorro stats               # що вже зібрано
```

### Скільки це важить

Виміряно на 200 000 справжніх рядків, бо на двадцяти мільйонах різниця
вимірюється гігабайтами на чужому ноутбуці:

| Схема | Байт на рядок | На 20 млн процедур |
|---|---|---|
| Перша версія | 435 | 8,1 ГБ |
| Поточна | 220 | 4,1 ГБ |

Два рішення дали цю різницю. Замовники винесені в окрему таблицю: 31 870 унікальних
замовників повторювали свою 65-символьну назву в кожній своїй процедурі. Дати зберігаються
числом, а не рядком ISO: 32 байти і товстий індекс перетворились на 8 байтів і тонкий.

Двійковий ідентифікатор замість тридцяти двох шістнадцяткових символів зекономив би ще
33 байти на рядок, і від нього відмовились свідомо: hex-ідентифікатори лежать у посиланнях,
логах і аргументах інструментів, а перетворення на кожній межі це більше місць для помилки,
ніж вартує економія.

Індекс це кеш. Якщо схема зміниться, сервер не читатиме стару базу мовчки: він скаже,
що її треба зібрати заново. Тихо відповідати на запитання за застарілою розкладкою гірше,
ніж відмовитись.

Для щоденного оновлення досить одного `update`. Він читає лише те, що змінилось
після минулого проходу, тим самим кодом, що й повний обхід: окрема «інкрементальна»
реалізація з часом розійшлася б із основною і почала губити зміни.

Приклад запису в cron:

```
30 4 * * * cd /шлях/servers/prozorro && node dist/cli.js update --enrich=2000
```

Навіщо він потрібен:

**Зіставлення номера з ідентифікатором.** Без індексу давню процедуру за номером `UA-…`
знайти неможливо взагалі. З індексом це пошук за ключем: виміряно 4,6 мс на номер
при 123 000 процедур.

**Фільтри, яких у джерела немає.** За ЄДРПОУ замовника, за кодом CPV, за періодом.
Джерело такі параметри приймає і мовчки ігнорує.

**Українська морфологія.** FTS5 порівнює токени буквально, тому «дорога» не знаходить
«доріг». Індекс зберігає поруч оригінальну назву й нормалізовану форму, тому обидва
запити дають той самий результат.

Збагачення йде пулом у чотири одночасні запити з паузою, близько двадцяти процедур
на секунду. Один за одним було б у чотири рази повільніше, більший пул перетворив би
доливання на навантаження для державного сервісу.

Краулер ходить сторінками по 1000 записів з паузою і зберігає курсор після кожної:
перерваний обхід продовжується з того ж місця, а не починається спочатку.
Проходи історії та свіжого мають окремі курсори, тому не затирають один одного.

Поки індекс неповний, `proyav_search_index` повертає частку покриття разом із результатами,
щоб асистент бачив, що дивиться не на весь корпус, і міг перемкнутись на пошук джерела.

## Відоме обмеження

Пошук знає процедури за номером `UA-…`, центральна база — за внутрішнім id, і зіставлення
між ними джерела не дають. Сервер обходить це так: іде стрічкою змін від сьогодні назад
і зупиняється, щойно записи стають старішими за дату видачі номера, бо раніше свого створення
процедура змінюватись не могла.

Для активних процедур це працює за пів секунди. Процедуру, яку не чіпали роками, так не знайти:
її запис у стрічці лежить далеко в минулому. Саме цей випадок і закриває локальний індекс,
якщо він побудований на потрібний період.

## Розробка

```bash
npm install
npm run build

```

### Навіщо контрактні тести

Обидва джерела недокументовані. Якщо формат відповіді зміниться, сервер поверне порожнечу,
і асистент скаже людині, що закупівель немає, — найгірший можливий результат для інструмента
про прозорість. Тому кожен перевірений факт про джерело зафіксований тестом із поясненням,
що саме зламається. CI ганяє їх щодня за розкладом.

## Межі відповідальності

Сервер показує факти з відкритих джерел. Він не виносить висновків: відхилення ціни від схожих
закупівель або збіг у складі учасників це привід перевірити уважніше, а не доведене порушення.
