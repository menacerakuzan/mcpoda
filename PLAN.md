# ПРОЯВ: план роботи

Оновлено 25.08.2026. Це робочий документ: кожна фаза має критерій приймання,
кожне рішення має причину, кожен ризик має відповідь.

---

## 1. Принципи

Вони визначають усе решта, тому стоять першими.

**Перевіряємо джерело живими запитами, а не документацією.** Уже перший день роботи дав
чотири розбіжності між тим, як API описане, і тим, як воно поводиться. Кожен факт у цьому
документі має дату перевірки.

**Сервери лише читають.** Жодного tool, який щось змінює в державному реєстрі. Це не технічне
обмеження, а межа відповідальності: ми показуємо опубліковане, а не втручаємось.

**Показуємо факти, висновок робить людина.** Відхилення ціни чи збіг у складі учасників це
ознака, яку варто перевірити, а не доведене порушення. Формулювання інструментів і відповідей
мають це тримати, бо на державних даних ціна помилки це чиясь репутація.

**Компактна видача.** Сира картка процедури важить десятки кілобайт. Модель отримує вижимку
і лічильники того, що лишилось за кадром, щоб могла свідомо попросити більше.

**Без ключів і реєстрації.** Дані вже відкриті законом. Додати логін означало б поставити
бар'єр там, де держава його зняла, і дізнатися, хто що шукає. Ми цього не хочемо.

**Не обіцяємо того, чого немає.** Поки сервер не працює, сторінка каже, що це чернетка.

## 2. Де ми зараз

### Зроблено

`servers/prozorro` — робочий MCP-сервер, 651 рядок, три інструменти:
`proyav_search_tenders`, `proyav_get_tender`, `proyav_recent_tenders`.
Перевірено наскрізним смоук-тестом, який піднімає сервер як MCP-клієнт і б'є по живих даних.

`web/` — лендинг і сторінка документації, задеплоєні на Vercel.

### Перевірені факти про джерела

Станом на 25.08.2026, усе підтверджено запитами.

| Що | Факт |
|---|---|
| Пошук `prozorro.gov.ua/api/search/tenders` | Тільки POST. `text` обов'язковий і непорожній |
| | `page` нумерується з 1, відповідь повертає його луною; без `page` каже `0` і віддає ту саму сторінку |
| | `per_page` приймається і мовчки ігнорується: рівно 20 записів завжди |
| | `status` працює як фільтр і приймає масив |
| | `cpv` та `edrpou` приймаються і мовчки ігноруються |
| | `region` очікує числовий код, поводиться неконсистентно, непридатний |
| | Стеля видачі: 10 000 збігів на запит |
| Стрічка CDB `public.api.openprocurement.org/api/2.5/tenders` | `limit` до 1000, `descending=1` |
| | `offset` приймає дату `РРРР-ММ-ДД` і unix-час |
| | `opt_fields` лише для `status`, `tenderID`, `procuringEntity`, `procurementMethodType` |
| | `title`, `value`, `items`, `awards` у стрічку не потрапляють ніколи |
| | Швидкість: 1000 записів за 0,54 с, тобто близько 1,85 млн записів за годину |
| Картка CDB `/tenders/{uuid}` | Повний запис, десятки кілобайт |
| Природа стрічки | Це стрічка змін: процедура стоїть на місці своєї **останньої** зміни, не створення |
| Розкриття учасників | Особи учасників публікуються лише після визначення переможця |

### Головне обмеження, з якого випливає весь план

Пошук знає процедури за номером `UA-…`, центральна база — за внутрішнім id,
і зіставлення між ними жодне джерело не дає.

Зараз сервер обходить це проходом стрічкою назад від сьогодні з зупинкою на даті видачі
номера. Для активної процедури це пів секунди. Процедуру, яку не чіпали роками, так не
знайти взагалі: її запис лежить у минулому, за межами розумного сканування.

Тобто **без власного індексу частина відкритих даних для нас недосяжна**. Це не питання
швидкості, це питання доступності. Індекс — не оптимізація, а умова роботи.

### Розсинхрон, який треба закрити

Сторінка документації показує чернетку з 24 інструментів. Реально працює три.
Плашка «чернетка специфікації» стоїть, але тримати такий розрив довго не можна.

## 3. Архітектура

```
джерела            індекс              проєкції          інструменти        клієнт
─────────          ──────              ────────          ───────────        ──────
search API    ┐                                      ┌ search_tenders
CDB стрічка   ├──► SQLite + FTS5 ──► компактні   ────┼ get_tender      ──► будь-який
CDB картка    ┘    (id ↔ UA-номер,     картки         ├ price_benchmark     MCP-клієнт
                    заголовки,                        └ …
                    сторони)
```

### Структура репозиторію

```
packages/core/        спільне: http, помилки, проєкції, типи, утиліти дат і грошей
servers/prozorro/     сервер закупівель
servers/nazk/         сервер декларацій (фаза 5)
web/                  лендинг і документація
```

Спільне ядро окремим пакетом, бо http-шар, обробка помилок і принцип проєкцій однакові
для обох серверів, а копіювання розійдеться вже на другому виправленні.

### Чому SQLite

Файлова база без сервера, працює на машині користувача, нічого не треба піднімати.
Модуль FTS5 дає повнотекстовий пошук по нашому індексу, а значить **знімає стелю 10 000
збігів**, яка є у джерела. Тобто індекс не тільки закриває проблему зіставлення id,
а й робить пошук кращим за оригінальний.

### Транспорт

Зараз stdio: сервер живе на машині користувача, дані нікуди не йдуть, лімітів немає.
Streamable HTTP — після того, як з'явиться потреба і відповіді на питання про навантаження.

## 4. Фази

### Фаза 1. Фундамент і захист від змін у джерелах

**Навіщо.** Ми стоїмо на двох недокументованих API. Будь-яка їхня зміна ламає нас мовчки:
модель отримає порожню відповідь і скаже людині, що закупівель немає. Це найгірший сценарій
для інструменту про прозорість.

**Що робимо.**
- Контрактні тести: кожен перевірений факт з таблиці вище стає тестом. `per_page` ігнорується?
  Тест це фіксує. Почне працювати — тест впаде, і ми дізнаємось, а не здогадуватимемось.
- Юніт-тести на проєкції та резолвер номера.
- CI на GitHub Actions: збірка і тести на кожен пуш, контрактні тести раз на добу за розкладом.

**Свідомо не робимо зараз.** Винесення `packages/core` відкладено до появи другого сервера:
абстракція з одним споживачем це здогадка про майбутнє, а не спрощення. Http-шар і проєкції
живуть у `servers/prozorro`, поки не з'явиться реальна друга потреба.

**Критерій приймання.** Зелений CI. Штучна зміна формату відповіді джерела валить тест.

**Перевірено 25.08.2026.** CI зелений в обох роботах. Критерій підтверджено мутаціями:
підміна розміру сторінки, зникнення `tenderID` зі стрічки, зміна межі показу позицій
і повернення історичного бага з регістром у резолвері — кожна валить свій тест
із зрозумілим повідомленням. Під час перевірки знайдено пробіл: резолвер номера лежав
усередині інструмента й був непокритий, хоча саме в ньому був баг. Винесено в `src/resolve.ts`
з підставною стрічкою і покрито вісьмома тестами. Разом 21 юніт-тест і 11 контрактних.

### Фаза 2. Індекс Prozorro

**Навіщо.** Знімає обмеження зіставлення id і стелю пошуку.

**Що робимо.**
- Краулер стрічки з курсором у базі: перервали, запустили далі з того ж місця.
  Обов'язково резюмований, бо повний обхід за виміряною швидкістю це багато годин.
- Легкий шар індексу з того, що стрічка віддає без додаткових запитів:
  `id`, `tenderID`, `dateModified`, `status`, `procurementMethodType`, ЄДРПОУ і назва замовника, регіон.
- Другий шар, збагачення карток: `title`, `value`, CPV — окремим запитом на процедуру,
  за пріоритетом (спочатку активні та свіжі), у фоні, з обмеженням частоти.
- FTS5 по заголовках і предметах.
- Інкрементальне оновлення: щоденний догон від збереженого курсора.

**Відкрите питання, яке закриє сам краулер.** Точний обсяг корпусу невідомий: стрічка
впорядкована за датою зміни, тому вибірками його не порахувати. Перший повний прохід
і дасть цифру. Краулер має логувати прогрес, щоб ми побачили реальний масштаб.

**Критерій приймання.** Будь-який номер `UA-…` резолвиться швидше за 50 мс.
Пошук по індексу знаходить те, чого джерело не показує через стелю 10 000.

**Стан 25.08.2026: виконано частково.**

Зроблено: схема на вбудованому `node:sqlite` з FTS5, краулер з окремими курсорами для історії
та свіжого, збагачення карток найновішими першими, пошук по індексу з фільтрами за ЄДРПОУ,
CPV, періодом і сумою, два нові інструменти, 45 тестів без мережі.

Критерій швидкості перевищено: резолв номера 4,6 мс на 123 000 процедур замість межі 50 мс.

Не закрито: повний обхід історії. Стрічка виявилась щільнішою за очікування, і на ділянці
кінця 2016 року курсор рухається на хвилини реального часу за сторінку. Обсяг корпусу
досі невідомий, його покаже лише повний прохід. Тому за замовчуванням радимо `crawl --recent`:
індекс стає корисним одразу, а історія доливається окремо.

Знайдено і виправлено по дорозі: `pragma busy_timeout` виставлявся після `journal_mode = wal`,
через що другий процес падав з «database is locked» замість очікування; підрахунок нових
записів поза транзакцією давав відʼємні числа при паралельному запису; FTS5 вимагає подвійних
лапок для фраз, а не одинарних, як SQL.

### Фаза 3. Аналітика

**Навіщо.** Це те, заради чого люди приходять: не «покажи тендер», а «ми не переплачуємо?».

**Що робимо.**
- `proyav_price_benchmark`: ціна процедури проти схожих. Схожість за CPV, одиницею виміру
  і періодом. У відповіді обов'язково видно вибірку: скільки процедур, за який період,
  медіана і розкид, а не одне число.
- `proyav_aggregate_spend`: обсяги за CPV, замовником, регіоном, періодом.
- `proyav_compare_buyers`: кілька замовників на однаковому предметі.

**Методологічна пастка, яку треба тримати.** Порівнювати можна лише однакові одиниці виміру.
«Ремонт дороги» за кілометр і за квадратний метр це різні числа, і зіставлення їх дасть
неправдиву сенсацію. Інструмент має відмовлятись рахувати, коли одиниці не збігаються,
і казати чому.

**Критерій приймання.** Розрахунок відтворюваний, вибірка видима, різні одиниці не змішуються.

### Фаза 4. Звʼязки і перевірка тендерів

**Навіщо.** Це витрина можливостей, обіцяна на лендингу.

**Що робимо.**
- Сигнали афілійованості учасників: спільні телефони, пошта, адреси, час подання пропозицій.
- Робота **тільки із завершеними процедурами**, бо до визначення переможця особи учасників
  не публікуються. Інструмент має пояснювати це, а не мовчки повертати порожнечу.
- Граф зв'язків через ЄДР: спільні засновники та керівники, з датами.

**Рамка, від якої не відступаємо.** Жоден інструмент не вживає слів «змова» чи «порушення».
Формулювання: ознака, збіг, привід перевірити. Спільна адреса може означати бізнес-центр.
Близький час подання може означати дедлайн. Відповідь має нести цю обережність у собі,
бо її читатиме модель, яка потім говоритиме з людиною.

**Критерій приймання.** Ознаки супроводжуються поясненням, чому вони можуть бути невинними.

### Фаза 5. Сервер НАЗК

**Навіщо.** Друга половина обіцянки.

**Що робимо.**
- **Спочатку правова записка, потім код.** Декларації публічні за законом, але це
  персональні дані. Треба зафіксувати: що саме дозволено віддавати, чи є обмеження на
  автоматизовану обробку, чи потрібне маркування джерела. Це рішення не інженерне.
- Мінімізація: віддаємо лише опубліковане, не збагачуємо сторонніми джерелами,
  не будуємо профілів поза межами декларацій.
- Порівняння років однієї особи як окремий інструмент.

**Критерій приймання.** Правова записка узгоджена до першого рядка коду сервера.

### Фаза 6. Публікація

**Що робимо.**
- `@proyav/prozorro` і `@proyav/nazk` у npm, щоб конфіг зі сторінки нарешті працював.
- Синхронізувати сторінку документації з реальністю: працює, у роботі, заплановано.
- Зняти плашку «чернетка», коли вона перестане бути правдою.
- Запис реального діалогу як доказ роботи.

**Критерій приймання.** Людина копіює конфіг зі сторінки, вставляє і воно працює.

## 5. Ризики

| Ризик | Чому реальний | Що робимо |
|---|---|---|
| Недокументоване API змінюється | Уже бачили чотири розбіжності за день | Контрактні тести щодня, деградація з поясненням замість порожньої відповіді |
| Модель робить висновок про порушення | Вона говорить упевнено за замовчуванням | Обережні формулювання у відповідях і в `instructions` сервера |
| Навантаження на державні сервіси | Краулер це десятки тисяч запитів | Обмеження частоти, `User-Agent` з контактом, кеш, нічний догон |
| Обсяг даних більший за очікуваний | Точна цифра невідома | Резюмований курсор, поетапне збагачення, вимір під час першого проходу |
| Персональні дані НАЗК | Публічність не дорівнює вседозволеності | Правова записка до коду, мінімізація складу полів |
| Хибна сенсація через одиниці виміру | Різні одиниці дають різницю в рази | Відмова рахувати при розбіжності одиниць |
| Проєкт сприймуть як «ще один чат-бот» | Так уже питали | Схема потоку на лендингу, `instructions` сервера |

## 6. Чого не робимо

- Не робимо власну модель.
- Не збираємо даних про людей понад опубліковане державою.
- Не виносимо звинувачень і не рахуємо «рейтинги корупційності».
- Не ухвалюємо рішень за тендерні комітети.
- Не тримаємо персональних даних довше, ніж потрібно для відповіді.

## 7. Питання, на які потрібні рішення

1. Правова рамка НАЗК: хто в департаменті це підтверджує і в якій формі.
2. Де живе індекс: лише на машині користувача чи є спільна копія на сервері.
3. Чи публікуємо npm-пакети від імені ОДА і хто власник scope `@proyav`.
4. Домен: `proyav.od.ua` чи інший.
5. Публічність репозиторію на цій стадії.
